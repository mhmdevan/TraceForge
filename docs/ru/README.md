## 1. О проекте

TraceForge — это **контролируемый экспериментальный стенд** (а не очередное демо
микросервисов). Его задача — **измерить**, а не предположить, две вещи:

1. **Стоимость наблюдаемости (RQ1):** сколько ресурсов (задержка, CPU, память, объём
   телеметрии) добавляют метрики, логи и трассировки.
2. **Ценность наблюдаемости для обнаружения сбоев (RQ2):** насколько быстрее система
   обнаруживает сбой при наличии телеметрии.

Ключевая идея — **инкрементальное** измерение: один и тот же код запускается на **пяти**
уровнях наблюдаемости относительно **истинной неинструментированной базовой линии**, а
результаты анализируются статистически строго и **воспроизводимо**.

## 2. Область исследования и ограничения

Это научно честный, но **ограниченный** артефакт:

- Результаты **нельзя обобщать** на все микросервисные системы. Они характеризуют **данную**
  нагрузку, **данную** реализацию телеметрии (Node.js/TypeScript), **данное** оборудование
  и **данный** протокол эксперимента.
- **RQ2 измеряет только обнаружение (MTTD), а не полную «отлаживаемость».** Анализ
  первопричин (root-cause) требует исследования с участием операторов и вынесен в будущую
  работу.
- Все измерения выполнены на **одной машине, одном стеке, одной нагрузке** (см. §9).

Указание этих границ — это **научная честность**, а не недостаток метода.

## 3. Архитектура

Предметная область — обработка транзакций: один запрос проходит через запись в БД,
кэширование, внешний HTTP-вызов и асинхронную обработку события.

```text
POST /transactions
  → API Gateway
  → Transaction Service
       → PostgreSQL (запись)   → Redis (кэш)
       → Payment Service (HTTP) → RabbitMQ (публикация)
            → Worker Service (потребление) → PostgreSQL (сохранение события)
```

| Сервис              | Назначение                                                            |
| ------------------- | --------------------------------------------------------------------- |
| API Gateway         | Публичный HTTP-API; проброс correlation-id и контекста трассировки    |
| Transaction Service | Основной поток; запись в PostgreSQL, кэш Redis, вызов оплаты, событие |
| Payment Service     | Симуляция авторизации платежа; внедрение сбоев                        |
| Worker Service      | Потребление событий из RabbitMQ и их сохранение                       |

Пять общих пакетов (`contracts`, `config`, `logger`, `metrics`, `tracing`) централизуют
типы, конфигурацию, логирование, реестр Prometheus и SDK OpenTelemetry. Каждый слой
наблюдаемости становится «no-op», если его режим выключен, поэтому **во всех режимах
работает один и тот же бинарный код** — меняется только инструментирование.

## 4. Режимы наблюдаемости

Глубина наблюдаемости выбирается одной переменной окружения `OBS_MODE`:

| `OBS_MODE`            | Метрики | Логи | Трассировки | Collector |
| --------------------- | :-----: | :--: | :---------: | :-------: |
| `none` (базовая)      |    —    |  —   |      —      |     —     |
| `metrics`             |    ✓    |  —   |      —      |     —     |
| `metrics_logs`        |    ✓    |  ✓   |      —      |     —     |
| `metrics_logs_traces` |    ✓    |  ✓   |      ✓      |     —     |
| `otel_full`           |    ✓    |  ✓   |      ✓      |     ✓     |

## 5. Технологический стек

- **Язык/каркас:** TypeScript (строгий режим), NestJS, монорепозиторий pnpm
- **Хранилища:** PostgreSQL, Redis, RabbitMQ, MongoDB (для эксперимента с индексами)
- **Наблюдаемость:** OpenTelemetry, Prometheus, Loki, Jaeger, OTel Collector, Grafana
- **Нагрузка:** k6 (открытая модель — постоянная интенсивность запросов)
- **Оркестрация:** Docker Compose, Docker Swarm, Kubernetes (манифесты)
- **Статистика:** собственная библиотека (доверительные интервалы bootstrap, критерии
  Манна–Уитни и Краскела–Уоллиса, размер эффекта — дельта Клиффа), покрытая модульными тестами
- **Графики:** SVG без внешних зависимостей

## 6. Методология

- **Открытая модель нагрузки** (постоянная интенсивность запросов): медленная
  (инструментированная) система **не получает облегчённую** нагрузку — это корректная модель
  для измерения серверных накладных расходов.
- **N = 10** повторений на режим, в **случайном порядке** режимов; разогрев отбрасывается;
  образы пересобираются из текущего кода.
- **Непараметрическая статистика** (распределения задержек тяжелохвостые): медиана и IQR,
  доверительный интервал медианы (bootstrap, 5000 ресэмплов), критерий Краскела–Уоллиса
  между режимами, критерий Манна–Уитни против базовой линии, дельта Клиффа как размер
  эффекта. Правило решения: если 95 %-й ДИ режима **не пересекается** с ДИ базовой линии —
  отличие значимо.

## 7. Эксперименты и результаты

Все числа — **измеренные** (см. `docs/claims-to-evidence.md` для соответствия
«утверждение → команда → данные»).

### 7.1 Накладные расходы наблюдаемости (RQ1)

Накладные расходы по **CPU** (медиана, N = 10):

| Режим                   | CPU % [95% ДИ]    | Накладные | Значимо?                  |
| ----------------------- | ----------------- | --------: | ------------------------- |
| Базовая линия           | 5.6 [5.3, 7.2]    |         — | —                         |
| Метрики                 | 8.3 [5.2, 13.6]   |     +48 % | **нет** (ДИ пересекаются) |
| Метрики + Логи          | 14.9 [13.7, 19.6] |    +164 % | **да** (p < 0.001)        |
| Метрики + Логи + Трасс. | 8.9 [8.2, 13.2]   |     +59 % | да (p = 0.003)            |
| Полный OpenTelemetry    | 8.5 [7.2, 9.6]    |     +51 % | пограничный случай        |

**Выводы:**

1. **Метрики практически бесплатны** — статистически неотличимы от базовой линии.
2. **Структурированное логирование — главный источник накладных расходов** (CPU +164 %,
   медианная задержка +177 %, p < 0.001, дельта Клиффа = 1.0) и пиков задержки.
3. **Полный конвейер OpenTelemetry** несёт больше всего телеметрии, но удерживает CPU на
   уровне трассировок (+51 %) с наименьшей дисперсией задержки — благодаря пакетному
   асинхронному экспорту.

### 7.2 Кривая «задержка–пропускная способность»

Свип по интенсивности (60 → 480 запр/с) показывает **точку насыщения** каждого режима:

- **Базовая линия** выдерживает все 480 запр/с (p95 ≈ 5–9 мс), насыщения нет.
- **Метрики + Логи** отстают после ~240 запр/с.
- **Полный OpenTelemetry** насыщается **раньше всех** — около **220 запр/с** (меньше
  половины базовой линии), p95 уходит в секунды.

Главный практический вывод: тяжёлые конвейеры в первую очередь **снижают максимальную
пропускную способность**, а не добавляют фиксированный налог на каждый запрос.

### 7.3 Объективное обнаружение сбоев (RQ2, MTTD)

MTTD — время от внедрения сбоя до срабатывания алерта Prometheus, **без участия человека**:

| Сбой                | Режим         | Обнаружен | До pending | До firing |
| ------------------- | ------------- | --------- | ---------: | --------: |
| Ошибки оплаты (500) | Базовая линия | **нет**   |          — |         — |
| Ошибки оплаты (500) | Метрики       | да        |      9.4 с |    70.3 с |
| Медленная оплата    | Базовая линия | **нет**   |          — |         — |
| Медленная оплата    | Метрики       | да        |      9.7 с |    72.2 с |

**Это «ступенька», а не градиент:** без конвейера метрик сбой реален и серьёзен (12 % ошибок
или p95 ≈ 1 с), но **автоматически необнаружим**. С метриками — обнаружение за ~9 с (pending)
и оповещение за ~70 с (firing).

### 7.4 Индексирование БД (1 млн строк)

PostgreSQL, 7 стратегий × 5 запросов, 1 000 000 транзакций:

- Индексы по ведущим столбцам превращают полное сканирование 1 млн строк в точечный доступ
  (Q1: 24.5 мс → **0.11 мс**, +99.6 %, ~16 строк вместо 1 млн).
- Цена записи растёт: **+19 %** (частичный индекс) … **+322 %** (трёхстолбцовый); размеры
  индексов 3.9–47.4 МиБ.
- Сравнение SQL/NoSQL ведётся по **структурной метрике** (просмотрено строк/документов), а не
  по несравнимой задержке: например, 16 строк против 11 документов. Утверждения «движок X
  быстрее Y» **не делаются**.

### 7.5 Сравнение оркестраторов

Compose / Swarm / Kubernetes сравниваются по запуску, масштабированию и восстановлению на
одинаковом стеке (подробности — `docs/orchestration-comparison.md`).

## 8. Запуск и воспроизводимость

```bash
pnpm install
pnpm typecheck && pnpm lint && pnpm test   # 52 теста
pnpm env:capture                            # записать окружение → results/environment.json
```

Команды экспериментов (каждый сам поднимает и останавливает стек):

```bash
pnpm load:run && STATS_DATASET=load pnpm stats:report   # RQ1
pnpm sweep:run                                          # кривая насыщения
pnpm mttd:run                                           # RQ2 (обнаружение)
INDEXING_TRANSACTIONS=1000000 INDEXING_USERS=100000 INDEXING_REPS=15 pnpm indexing:run
pnpm orchestration:run
```

Полное руководство по воспроизводимости — `docs/reproducibility.md`. Быстрая
демонстрация (5 минут) — `docs/demo.md`.

## 10. Что можно защищать

- **Методология:** инкрементальное измерение стоимости наблюдаемости с истинной базовой
  линией и статистической строгостью (открытая модель, N = 10, ДИ, непараметрические тесты,
  размеры эффекта).
- **Объективная метрика обнаружения сбоев (MTTD)** вместо субъективных оценок.
- **Кривая «задержка–пропускная способность»** с точкой насыщения — нагрузочно-устойчивый
  результат.
- **Воспроизводимый артефакт** (код + данные + графики + DOI), где каждый результат
  воспроизводится из исходников.
- **Честно обозначенные границы** (§2) и явный план будущей работы (исследование первопричин
  с операторами, генератор нагрузки вне хоста, поэлементное чередование повторов).
